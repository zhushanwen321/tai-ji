# 框架低频控件使用频率盘点（PanelHeader 控件分组的前置产品决策）

状态：待立项（产品决策，非设计决策）。登记来源：ui-signal-density 设计 D6 移出记录（§3.0 第 4 条）——框架控件分组方案因「不解决自己被分配的『框架密度过高』病症」整体移出该设计范围

## 背景

ui-signal-density 设计曾提出 `PanelHeader.vue` 的 13 项控件按三组归位（导航组 / 视图组 / 窗口组，组间留白）+ 目录段与分支段同名时合并为一段。该方案被移出的原因（设计自认）：只做「DOM 顺序重排 + 组间留白 + 少一个文本槽」，不减少控件数量，治不了「框架密度过高」；真正把 chrome 做薄需要先知道哪些控件低频——而这需要使用频率数据。

## 待做

1. **控件使用频率盘点**：对顶栏（`PanelHeader.vue`）与输入区底栏控件做使用频率采集（入口埋点或用户访谈），产出「高频 / 低频」清单。设计阶段「低频控件」清单自认缺位，这是后续任何分组 / 收纳决策的数据前置。
2. **基于盘点结果重新裁决**：低频控件是否收进菜单、顶栏是否还有分组价值、入口是否该常驻。注意两条既有边界：① 「前进 / 后退 / git 入口 / 抽屉开关」是 P0/P1 面的功能入口，收纳前须验证低频结论，不能凭观感收；② composer 的 `AddMenuPopover` 与顶栏不同区，顶栏没有现成 `+` 菜单，「收进 + 菜单」在顶栏语境没有现成宿主。
3. 与 [sidebar-shortcut-hints-on-demand-revisit.md](sidebar-shortcut-hints-on-demand-revisit.md)（侧栏快捷键提示是否改按需）同题合并裁决——同一题：入口该不该常驻。
